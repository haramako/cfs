# ストレージのガーベージコレクション（計画）

**状態: 計画（2026-10-25 オーナー指示）。実装は未着手。**

## 背景

キャビネット（S3 など）の `data/` には中身が増える一方で、どのタグからも使われなくなった中身を消す仕組みがない。`cfs serve` で HTML などのアーティファクトを次々に上げる用途（[公開サーバーの計画](2026-10-25-public-serve-plan.md)）では、特に早く溜まる。

対象は、当面の対応ストレージである **S3 とローカル**（[対応ストレージを絞る方針](2026-10-25-storage-scope-file-and-s3-only.md)）。

## 今の作りで、そのまま消すと壊れる理由（コードで確認）

1. **`upload` は、手元のキャッシュで「変更なし」と判断したファイルについて、ストレージにその中身がまだあるかを確かめない**（`internal/cfs/client.go` の `AddFile`。更新日時とサイズが同じなら前回のハッシュをそのまま使う）。GC で消された中身を、新しいファイル一覧が指してしまう
2. **ファイル一覧（バケット）自体も `data/` に置かれている**（`UploadBucket` が `"*bucket*"` として `data/` に保存）。中身とファイル一覧を区別できないので、「どれがファイル一覧か」を GC が判断できない
3. **アップロードの途中**は、中身を先に上げ、ファイル一覧とタグを最後に上げる。その間に GC が走ると、まだどこからも参照されていない新しい中身や、重複として使い回そうとしている既存の中身を消しうる

## 方針

### 形式の変更（互換性は当面不要なので素直に変える）

- **ファイル一覧を `data/` から分けて、`bucket/xx/yyyy...` に置く**。GC の起点を一覧で取れるようにする
- タグは今のまま `tag/<名前>`（中身はファイル一覧のハッシュ）

### 何を残すか（マーク）

次の「起点」から辿れる中身をすべて残す。

- **すべてのタグ**が指すファイル一覧と、その中身
- **保持期間（例: 30 日）以内に作られたファイル一覧**と、その中身（タグが上書きされても、最近の一覧は残す。手元のキャッシュやハッシュで直接指定している人を守るため）

### 何を消すか（スイープ）

次の条件を**すべて**満たすものだけを消す。

- 起点から辿れない
- ストレージ上の更新日時が保持期間より古い（アップロード途中の新しい中身を守る）
- **前回の GC でも消す候補だった**（2回連続で未参照。1回目は候補の一覧をキャビネットに保存するだけにし、2回目で消す。アップロード途中の使い回しとの競合を防ぐ）

### `upload` 側の対応

- 手元のキャッシュ（`~/.cfs/cache/`）が保持期間の半分より古い場合は、キャッシュを信用せず、`--force` と同じく全ファイルを調べ直す（存在確認も行う）。キャッシュのファイル一覧が保持期間内なら、その一覧が起点として残っているので、中身も残っている
- 保持期間はキャビネットの設定として1か所で決める（例: キャビネットに `config` を置く、または `.cfsenv`）。GC と `upload` が同じ値を使う

### 安全装置

- **読めないファイル一覧が1つでもあれば、何も消さずに中止する。** 暗号鍵の違いなどで一覧が読めないまま進むと、その中身を全部消してしまうため
- `--dry-run` で、消す予定の件数と合計サイズを表示する。最初の数回は dry-run で確かめる運用にする
- 消したものの一覧（ハッシュとサイズ）をログとしてキャビネットか手元に残す
- S3 のバージョニングが有効なバケットでは、削除しても「削除マーカー」が付くだけで容量は減らない。古いバージョンを消すライフサイクルルールを合わせて設定する（docs に書く）

### タグの整理（別コマンド）

GC は「どこからも使われていない中身」を消すだけで、**タグ自体は消さない**。古いアーティファクトのタグを消すために、次を足す。

- `cfs tag ls`（タグ名、指すハッシュ、更新日時）
- `cfs tag rm <タグ>`
- 必要なら、名前の規則と期間で一括削除（例: `report-*` で 30 日より古いもの）

### コマンド

```
cfs gc [--dry-run] [--retention 30d]
cfs tag ls
cfs tag rm <タグ>
```

定期実行は、CI の定期ジョブ（GitHub Actions の `schedule`）などで行う。

### 実装の形

- `Storage` インターフェースに、一覧（`List(prefix)`）と削除（`Delete(keys)`）を足す。S3 は ListObjectsV2 と DeleteObjects（1回 1000 件まで）、ローカルはファイルの列挙と削除
- 必要な S3 の権限: `s3:ListBucket`、`s3:GetObject`、`s3:DeleteObject`
- 後から別のストレージを足すときも、この2つを実装すれば GC が使える

## テスト

- ローカルのキャビネットで: 複数のタグと上書き、保持期間の境界、2回連続ルール、読めない一覧での中止、dry-run が何も消さないこと
- `upload` の手元キャッシュが古い場合に、存在確認をすること
- S3 は偽サーバーテストに List と DeleteObjects を足して確認する

## 関連

- 手元のダウンロードキャッシュ（`~/.cfs/datacache/`）も増える一方なので、大きさや古さで消す仕組み（`cfs cache clean` など）を別に検討する
- 公開サーバーの計画の「古いアーティファクトが溜まる」は、この計画（GC + タグの整理）で対応する

## 追記（2026-10-25）: 手元キャッシュとの両立の設計を変更

オーナーの指示で、本文の「`upload` 側の対応」（手元のキャッシュが保持期間の半分より古ければ調べ直す）を、次の設計に**置き換える**。あわせて、cfs の「バケット」を「マニフェスト」に改名する（[改名の方針](2026-10-25-rename-bucket-to-manifest.md)）ので、置き場所は `bucket/` ではなく **`manifest/xx/yyyy...`** にする。

### 本文の案の弱いところ

キャッシュの新しさをファイルの日時で判断するため、CI のキャッシュの復元や別マシンからのコピーで日時が当てにならない。また「保持期間」という時間の約束に頼るので、GC の設定を変えると前提が崩れる。

### 新しい設計

**GC 側の決まり: マニフェストがストレージに残っている間は、そのマニフェストから辿れる中身を消さない。**

- GC は、使われなくなったマニフェスト（どのタグからも指されず、保持期間より古いもの）を**先に**消す
- その中身は、**次の回の GC** で、残っているどのマニフェストからも辿れなければ消す（「マニフェストが先、中身は後」。間に最低1回分の間隔が空く）
- 本文の条件（保持期間より古い、2回連続で候補）は、中身にもそのまま適用する

**`upload` 側: 手元のキャッシュを使う前に、そのキャッシュが指すマニフェストがストレージにまだあるかを1回だけ確かめる。**

- 確かめる対象は、このマシンが前回の `upload` で置いたマニフェスト1つ。手元の `~/.cfs/cache/<名前>.hash` に、そのハッシュ（圧縮・暗号化後のデータのハッシュ）が保存されているので、`manifest/<ハッシュ>` の場所を1回問い合わせる（S3 なら HeadObject）
- **ある** → GC 側の決まりにより、そのマニフェストの中身は全部まだある。キャッシュをそのまま信用する（今と同じ速さ）
- **ない** → キャッシュを捨てて、全ファイルを調べ直す（`--force` と同じ）
- アップロードが終わると新しいマニフェストが置かれ、次回の「自分のマニフェスト」になる。使い回した中身は、新しいマニフェストから辿れるので守られる
- 今の `BucketFromFile` は `.hash` を読んでいないので、読むようにする

### これで守れる場面

| 場面 | どうなるか |
|---|---|
| 手元のキャッシュが古い・コピーされた・CI で復元された | 日時ではなく、マニフェストがあるかで判断するので関係ない |
| 確認の直後に GC がマニフェストを消した | 中身が消えるのは次の回（例: 翌日）なので、アップロードは間に合う |
| 他の人のアップロードで同じ中身を使い回した | アップロード途中は「保持期間より古い」「2回連続で候補」の条件で守られる |
| 自分のタグが他の人に上書きされた | 自分のマニフェストが保持期間内なら残る。消されていれば確認で気づいて調べ直す |

### 費用

`upload` 1回につき問い合わせが1回増えるだけ。「変更がなければ約1秒」はほぼ変わらない。必要な権限は `s3:GetObject`（または `s3:ListBucket`）。

### 採らなかった案

- 毎回、全ファイルの中身の存在を確かめる: 2000 ファイルで並列でも数秒かかり、速さの強みが消える
- 使い回した中身の日時をコピーで更新する: ファイル数ぶんの書き込みが毎回必要で、遅くて高い
- GC をやめて S3 のライフサイクルで古いものを消す: 使われているかを見ないので、使っている中身まで消える

### テストの追加

- マニフェストが消された後の `upload` が、全ファイルを調べ直すこと
- GC が「マニフェストが先、中身は次の回」の順で消すこと（同じ回にマニフェストと中身を両方消さないこと）
