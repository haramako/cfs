# cfs http を公開サーバーで動かす計画（認証・安全性・性能）

**状態: 検討中。方向性と性能改善を記録（2026-10-25）。認証の方式など未決事項あり（後述）。実装は未着手。**

## 背景

`cfs http`（オーナーは `cfs serve` と呼んでいる）を、パブリックなサーバーで動かしても問題ないようにしたい。認証は Google アカウントでのログインが望ましい。取引先の人も、その人の Google アカウント（Gmail など）で通したい。

今の `cfs http` は手元で確認するための作りで、そのままでは公開できない。

## 認証の方式（候補）

cfs 本体に OAuth を組み込まず、**前段の仕組みで Google ログインさせる**のがおすすめ。

### 案1: Cloud Run + IAP（Google Cloud で動かす場合）

- Cloud Run のサービスに直接 IAP を付ける（2026-03 に正式提供。ロードバランサー不要、`gcloud run deploy --iap --no-allow-unauthenticated`）。cfs のコード変更なしで Google ログイン必須になる
- 誰を通すかは IAM のロール「IAP-secured Web App User」（`roles/iap.httpsResourceAccessor`）で指定。個人（`user:tanaka@gmail.com`）、Google グループ、Google Workspace のドメインを登録できる
- 取引先の運用は、**Google グループを1つ作って IAM にはそれだけを登録し、メンバーで管理する**のがよい（グループで外部メンバーを許可しておく）
- **取引先（組織外）を通すには、自前の OAuth クライアントが必要。** IAP 既定の Google 管理の OAuth クライアントは同じ組織の人しか通さない。OAuth 同意画面は「外部」にする
- 組織のポリシー「ドメインで制限された共有」（`constraints/iam.allowedPolicyMemberDomains`）が有効だと、社外アカウントを IAM に登録できないので確認する
- 取引先の会社のアドレスが Google アカウントでない場合は、本人に「既存のメールアドレスで Google アカウントを作成」してもらう
- 念のため cfs 側で `X-Goog-IAP-JWT-Assertion` の署名を確かめれば、IAP を通らない直接アクセスを拒否できる
- キャビネットは S3 のままでよい（[対応ストレージを絞る方針](2026-10-25-storage-scope-file-and-s3-only.md) と矛盾しない）

### 案2: oauth2-proxy を前に置く（どこで動かしても使える）

- Google Cloud 側は、**最初の1回だけ** OAuth 同意画面（外部）と OAuth クライアント ID（ウェブアプリ、リダイレクト URI は `https://<ホスト>/oauth2/callback`）を作る。IAM や API の有効化は不要
- 通すメールアドレスは oauth2-proxy 側で管理する（`--authenticated-emails-file` に1行1アドレス、自社ドメインは `--email-domain`）
- 同意画面は「本番」に切り替える（「テスト」だとテストユーザーしかログインできず、一覧が2か所になる）。`openid` / `email` / `profile` だけなら審査は基本不要のはずだが、設定時に最新の条件を確認する
- Google グループで制限するには Admin SDK + ドメイン全体の委任が必要で面倒。メールアドレスの一覧で管理するほうが手軽
- 別途、Cookie の暗号化鍵（`--cookie-secret`）と HTTPS の終端が要る
- oauth2-proxy 自体はレスポンスをためずに流し、認証は Cookie の検証だけなので、大きいファイルでもほぼボトルネックにならない。大きいファイルを遅い回線で送る場合は、上流のタイムアウトを確認する

### 案3: cfs に組み込む（採らない方向）

`golang.org/x/oauth2` + `github.com/coreos/go-oidc/v3` で実装はできるが、セッション・ログアウト・鍵の入れ替え・セキュリティの確認を自前で持つことになり、案1・2 より手間と危険が大きい。

### 使い分け

- 誰を通すかを Google グループで管理したい、運用の手間を減らしたい → 案1（IAP）
- メールアドレスの一覧を手元のファイルで管理したい、Google Cloud 以外で動かしたい → 案2（oauth2-proxy）

## 公開向けの修正（どの案でも必要）

1. **XSS**: フォルダ一覧の画面で、ファイル名をエスケープせずに HTML へ埋め込んでいる（`cmd/cfs/cmd_http.go` の `renderDirectory`）。`html/template` に直す
2. **待ち受けアドレス**: `localhost:<port>` 固定。`--listen 0.0.0.0:8080` のように指定できるようにし、Cloud Run 用に環境変数 `PORT` にも対応する
3. **エラー処理**: 存在しないパスなどで panic している。404 / 500 を返す
4. **タイムアウト**: `http.Server` の読み込み・書き込み・アイドルのタイムアウトを設定する
5. **ファイル一覧のキャッシュ**: 下の性能改善を参照

## 性能改善（オーナー指示で計画に含める）

今の `cfs http` は、大きいファイルで次の問題がある。

- **ファイル全体をメモリに読んでから返している**（`Downloader.Fetch` が `[]byte` を返し、復号・展開してから書き出す）。500MB の `.ab` を10人が同時に取ると約 5GB 使う。ストレージから全部取り終わるまで最初の1バイトも返せない
- **アクセスのたびにタグとファイル一覧を取り直している**（`handleRoot` が毎回 `NewDownloader` と `LoadBucket` を呼ぶ）
- **Range（途中からの取得）に対応していない**。大きいファイルの再開や動画のシークができない

直し方:

- **ストリーミングにする**: ストレージから読みながら復号・展開してそのまま返す。zlib も AES-CFB も順番に読みながら処理できる。`Downloader` にバイト列ではなく `io.ReadCloser` を返す取得口を足す（[S3 から直接 sync する計画](2026-10-25-s3-direct-sync-plan.md) の `Fetcher` もストリームを返す形にそろえる）
- **無圧縮・無暗号のファイル（`.ab` など）は、手元のキャッシュから `http.ServeContent` で返す**: Range、`If-Modified-Since`、`Content-Length` を標準の仕組みで処理できる。中身がハッシュで決まるので、ETag にハッシュをそのまま使い、長い `Cache-Control` を付けられる
- **ファイル一覧をキャッシュする**: タグ → ハッシュは短い時間（数十秒など）、ハッシュ → ファイル一覧は中身が変わらないのでずっと（大きさに上限を付けて）キャッシュする
- Cloud Run では、一括で返すレスポンスは 32MiB までなので、ストリーミング（チャンク転送）で返すことが確実に必要になる
