# 大きなパックファイルと差分の扱い（アイデアの相談）

**状態: 相談のみ。実装はしていない（2026-10-25）。**

## 相談したこと

- cfs に似た成熟したアプリはあるか → Unity CCD（バケット・リリース・バッジ）、OCI レジストリ + ORAS、ostree、casync / desync、DVC、restic などを比べた。Unity の読み手が HTTP の GET だけで済む、という cfs の前提に合う置き換え先は、CCD くらい
- casync は「フォルダ全体を 1 本にまとめる」ところが cfs のパックに近く、中身で区切ったチャンクで、どの版からでも変わった部分だけを取れる（オーナーの理解とも一致）
- 大きなパックと差分の扱い方: 版どうしのパッチ / バイナリ差分（zstd --patch-from など）/ zsync 式の Range 取得 / チャンク置き場（casync・Steam 式）を比べた。圧縮・暗号化したものは差分が効かないので、チャンクに切ってからチャンクごとに圧縮・暗号化する必要がある
- パックには「小さなファイルのダウンロードをまとめる」目的もある → チャンクやファイルを 1 つずつ置く形では担保されない。小さなものを数 MB〜数十 MB のパックにまとめて置き、マニフェストに（パック, 位置, 大きさ）を書いて Range で取る形（restic や git の pack と同じ）なら両立できる。代わりに GC で repack が要る

## 分かったこと（結論）

- **Unity の AssetBundle は LZ4（128KB 固定のブロック圧縮）なので、大きさが変わる変更があると、そこから後ろのブロックが全部変わる。** LZMA は全体が 1 本の圧縮なので、なおさら。無圧縮でビルドすれば、変わったところ以外は「ずれるだけで同じバイト列」になるが、Addressables の流儀から外れる
- オーナーの結論: **アセットバンドルの変更は、ファイル単位で全然別になる**。したがって、チャンク単位の差分配信は、AssetBundle に対しては効果が薄い。今の cfs のファイル単位の重複排除が、AssetBundle には合っている
- 残る課題は「小さなファイルをまとめて取る」こと（パック + Range の案）と、変更が少数のバンドルに収まるようなバンドルの分け方

## 残り

- 必要になったら、実データで「1 回の更新で取るファイルの数と大きさ」と「リクエスト数」を測ってから、パック + Range の案を検討する
