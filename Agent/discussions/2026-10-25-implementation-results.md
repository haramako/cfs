## 形式 v2 で決めたこと（7）

- **ハッシュ**: SHA-256（64 文字）。ダウンロードしたデータは必ずハッシュで照合する
- **暗号化**: AES-256-CTR。`EncryptKey`（16 文字以上の任意の文字列）から HMAC-SHA256 で暗号鍵・IV 用の鍵・鍵 ID を導出。暗号文は `[版][鍵 ID 8B][IV 16B][本体]`。IV は `HMAC(iv_key, 平文)` の先頭 16 バイト（同じ中身なら同じ暗号文になり、重複の排除が効く）。鍵の入れ替えは `OldEncryptKeys` / `CFS_OLD_ENCRYPT_KEYS`。`EncryptIv` は廃止
- **署名**: Ed25519。秘密鍵は環境変数 `CFS_SIGNING_KEY` だけから読む（置き場所は運用開始時に決める、というオーナー回答どおり、仕組みだけ入れた）。検証は `.cfsenv` の `VerifyKeys`。`cfs keygen` で鍵を作る
- **配置**: `data/`、`manifest/`、`tag/`、`config.json`、`gc/`
- **GC**: [GC の計画](2026-10-25-garbage-collection-plan.md) の追記の設計どおり（タグ + 保持期間内を残す、2 回連続で候補、マニフェストが先・中身は後、読めない生きたマニフェストで中止、`upload` は前回のマニフェストの存在を確かめる）。候補にしてから消すまでの最短間隔は 1 時間
- **パックファイル**: 版 2（32 バイトの SHA-256）
- 人間向けの仕様を `docs/format.md` に書いた（Unity 側の実装の仕様書を兼ねる）
- 同じ中身を同時にアップロードすると Windows で失敗する問題が CI で見つかり、直した（`Client` は同じデータを 2 回送らない、`FileStorage` は同じ場所の書き込みを順番にし、競合で置き換えに失敗しても既にあれば成功とする）

## `cfs serve` で決めたこと（8）

- `http` を `serve` に改名（別名は残さない）。`--listen`（既定 `127.0.0.1:8000`）、`--tag-ttl`（既定 30 秒）
- タグ → ハッシュを短い時間、ハッシュ → マニフェストを LRU（64 件）でキャッシュ
- `http.ServeContent` で返す（`ETag` = 元のハッシュ、304、Range）。マニフェストのハッシュで指定した URL には `Cache-Control: immutable`
- ディレクトリ一覧は `html/template`（XSS 対策）。`.htm` の Shift_JIS は廃止。分からない拡張子は `application/octet-stream`、`X-Content-Type-Options: nosniff`
- panic せず 404 / 500。アクセスログに `X-Forwarded-Email` を出す
- **やっていないこと**: ストリーミング（中身は一度メモリに読む）。計画どおり後回し

## まだ残っていること

- **Unity 側のクライアントライブラリ**: 形式 v2（SHA-256、`manifest/`、マニフェストの形式、AES-256-CTR と鍵の導出、鍵 ID、署名の検証）に合わせて直す必要がある。仕様は `docs/format.md`。ライブラリはオーナーから受け取り待ち
- **署名の秘密鍵の置き場所**: 運用開始時に決める
- **`cfs serve` のストリーミング**: 後回し
- **手元のダウンロードキャッシュ（`~/.cfs/datacache/`）の掃除**: 未実装
- **実際の S3 での確認**: 偽サーバーのテストとローカルのキャビネットでしか確かめていない（S3 の権限や DeleteObjects、リージョン判定は実バケットで一度確認するとよい）
