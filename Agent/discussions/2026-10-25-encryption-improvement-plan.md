# 暗号化の改善（計画）

**状態: 計画のみ。実装は未着手。未確認事項が1つある（後述）。**

## 背景

アセットの暗号鍵（`EncryptKey` / `EncryptIv`）は、アセットを復号するクライアントにも組み込む前提で、オーナーは今はそれでよしとしている。より良い方法はあるかという相談。

前提として、オフラインで復号できる鍵をクライアントに入れる以上、本気で解析する相手からは守り切れない。どの方式でも同じなので、「何を守りたいか」で効く手が変わる。

## 現状の問題（コードを読んで確認）

1. **`.ab`（AssetBundle）は暗号化されていない。** `Bucket.GetAttribute` で `.ab` `.raw` `.pbx` `.mp4` は無圧縮・無暗号になる。最も大事なアセットが、配信先にそのままの形で置かれている
2. **IV が全ファイル共通の固定値。** AES-CFB で同じ鍵・同じ IV を使い回しているため、ファイル先頭 16 バイト同士の関係が漏れる。圧縮データの先頭は zlib ヘッダーで既知なので、全ファイルの先頭ブロックが少しずつ読める
3. **改ざん対策がない。** ダウンロード URL は http で、タグにも署名がない。経路上でファイル一覧ごと差し替えられうる。ハッシュは MD5 で、衝突を作る攻撃に弱い

## 改善案（効果が大きい順）

- **A. ファイル一覧に署名し、HTTPS で配信する（改ざん防止）** ← 最もおすすめ
  - アップロード時にファイル一覧（またはタグ）へ Ed25519 で署名し、クライアントには公開鍵だけを組み込む（公開鍵は漏れても問題ない）
  - ファイル一覧が正しければ各データはハッシュで照合できるので全体が守られる。そのためにハッシュを SHA-256 にする
  - クライアントに入れても破られない本物の安全性。改造アセットの差し込みも防げる
- **B. 未公開コンテンツの鍵を後から配る（事前リーク対策）**
  - コンテンツを鍵のグループに分け、未公開のグループは別の鍵で暗号化して先に配信。鍵は公開日にゲームサーバーからログイン済みクライアントへ渡し、メモリにだけ置く
  - 事前配信できるので、公開日のダウンロード集中も避けられる
  - cfs 側ではファイル一覧の各行に「鍵 ID」を持たせる拡張が要る
- **C. ファイルごとの IV と鍵の入れ替え（暗号の使い方を正す）**
  - IV は元ファイルのハッシュから作るか、ランダムに作ってデータの先頭に付ける
  - 鍵に ID を付けてバージョンごとに入れ替える。鍵が1つ漏れても被害はそのバージョンだけ
- **D. ダウンロード自体に認証を付ける（一括収集対策）**: CloudFront の署名付き Cookie / URL など。cfs 本体より配信側の設定
- **E. クライアント内での鍵の隠し方（難読化）**: 文字列のまま埋め込まない、IL2CPP など。手軽だが解析を面倒にするだけ

## 進め方

- **A と C は cfs だけで閉じて実装できる。**
- **B はゲームサーバーとの連携が必要なので、別の話として進める。**
- どれも、復号するクライアントライブラリ（Unity 側）の変更が必要。そちらのリポジトリも合わせて考える
- **互換性（2026-10-25 オーナー指示）**: 現在 cfs を使っているプロジェクトはないので、互換性は気にしなくてよい。旧形式を読めるようにする必要はなく、ファイル一覧の形式・暗号方式・ハッシュは素直に作り直してよい。使い始めたらオーナーが改めて指示する
