# 仕組み

## 用語

| 用語 | 意味 |
|---|---|
| キャビネット (cabinet) | アップロード先のストレージ全体。`s3://` か `file://` の URL で指定します |
| マニフェスト (manifest) | 1回のアップロードで記録される「ファイル一覧」です。どのパスのファイルがどの内容（ハッシュ）かを持っています。以前は「バケット」と呼んでいましたが、S3 のバケットとまぎらわしいので改名しました |
| タグ (tag) | マニフェストに付ける名前です。git のブランチやタグのように、名前から最新のマニフェストを引けます |
| ロケーション (location) | コマンドで「どのマニフェストか」を指定する引数です。タグ名か、マニフェストのハッシュ（32桁の16進数）を書きます |

## 内容アドレスで保存する

CFS は、ファイルを**中身のハッシュ（MD5）をもとにした場所**に保存します。考え方は git のオブジェクトの保存方法とよく似ています。

```
<キャビネット>/
  data/
    c5/9548c3c576228486a1f0037eb16a1b   # ファイルの中身（ハッシュの先頭2文字/残り30文字）
    ...                                 # ファイル一覧（マニフェスト）自体もここに保存されます
  tag/
    v1                                  # 中身はマニフェストのハッシュ（32文字のテキスト）
```

これにより、次のことができます。

- **同じ中身のファイルは1つだけ保存されます。** 別のパスでも、別のバージョンでも、別のプラットフォーム向けのファイルセットでも共有されます
- **一度アップロードした中身は、二度とアップロードしません。**
- **一度ダウンロードした中身は、二度とダウンロードしません。**
- **`data/` の下のファイルは、同じパスのまま中身が変わることがありません。** そのため、CDN や HTTP プロキシで安全にキャッシュできます。`tag/` は上書きされるので、キャッシュしないでください

## アップロードの流れ（`cfs upload`）

1. 前回アップロードしたときのファイル一覧を、手元のキャッシュから読み込みます
2. 指定したフォルダの中を順に調べ、変更があったファイルだけを見つけます
   - 更新日時とサイズが前回と同じなら、ファイルを読まずに「変更なし」とします（ファイルシステムによる誤差を考えて、1秒までのずれは許します）
   - 読み込んだ結果、ハッシュが前回と同じなら、更新日時だけを記録し直します
3. 変更があったファイルを圧縮・暗号化して、32並列でアップロードします。既にキャビネットにある中身は送りません
4. 今回見つからなかったファイルは一覧から消えます。つまり、ファイル一覧は**そのフォルダの完全なスナップショット**です
5. ファイル一覧自体もアップロードし、タグを指定していればタグをそのハッシュで更新します

変更がほとんどなければ、2回目以降のアップロードは一瞬で終わります。

## ダウンロードの流れ（`cfs sync`）

1. ロケーションがタグ名なら、`tag/<名前>` を取得してマニフェストのハッシュを得ます
2. ファイル一覧（マニフェスト）を取得します
3. 各ファイルの中身を取得して、復号・展開し、出力先に書き出します。既にダウンロード済みの中身は手元のキャッシュから使います

更新がなければ、通信はタグとファイル一覧の取得だけで終わります。

## ダウンロード元

- **アップロード**は、各ストレージの API を使って書き込みます（S3 は認証が必要です）
- **ダウンロード**は、何も指定しなければキャビネットから直接読みます。S3 のバケットは公開しなくて構いません
- 認証情報を持たせられない相手（ゲームのクライアントなど）に配るときは、CDN などで HTTP(S) で公開し、その URL をダウンロード元（`Url`）に指定します

詳しくは [ストレージ](storage-backends.md) を見てください。

## 圧縮と暗号化

ファイルは、アップロードするときに **zlib で圧縮 → AES で暗号化** されます。ストレージにも、手元のキャッシュにも、その状態で保存されます。ダウンロードしたときに自動で元に戻すので、使う側は普段意識する必要はありません。

設定と、どのファイルが対象になるかは [設定](configuration.md#圧縮と暗号化) を見てください。
